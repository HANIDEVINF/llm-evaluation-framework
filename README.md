# EvalGate — LLM Evaluation Workbench (Prototype)

EvalGate is an experimental workbench for thinking about quality, safety and tool-contract checks in LLM applications. The repository contains a small deterministic smoke-check runner plus an interactive UI with illustrative, preconfigured candidate responses.

> **Important status note:** the web UI is a frontend prototype. Its built-in candidate responses, latency/cost values and heuristic scores are demonstration data, not live model measurements. The included four-case suite is a smoke-test fixture, not a 150-case benchmark and not a validated safety or clinical evaluation. Do not cite the illustrative values as evidence of model quality.

## What is implemented

- A deterministic Python runner that evaluates response records supplied as JSONL.
- Required-phrase and prohibited-phrase checks for a small grounding example.
- A refusal-indicator smoke check, a synthetic identifier redaction check, and exact JSON equality for one tool-call contract.
- JSON reports with per-case reasons and a non-zero exit code when checks fail.
- A Next.js interface to explore evaluation dimensions; preset results in the UI are illustrative.

## What is not implemented yet

- The runner does not call a model or generate candidate responses.
- It does not implement an LLM-as-a-judge evaluator.
- It does not measure real latency, token usage, monetary cost, calibration, general safety, or broad faithfulness.
- Four cases are too few to support general conclusions; substring checks are deliberately simple and can produce false positives or false negatives.
- The frontend's preset candidate scores are not generated by the Python runner.

## Run the deterministic smoke checks

Requires Python 3.10 or later. No model API key is required.

~~~bash
python -m unittest discover -s tests -v
python scripts/run_eval.py --suite benchmarks/benchmark_suite_v1.json --responses examples/illustrative_responses.jsonl --config illustrative-fixture
~~~

The response file is deliberately named illustrative_responses.jsonl. It is only a fixture used to test the runner and **is not a real model run**. To evaluate a candidate, export one JSONL record per benchmark case in this format:

~~~json
{"case_id":"EVAL-001","response":"Paste the actual candidate response here."}
{"case_id":"EVAL-004","response":"Tool result summary","tool_call":{"function":"query_pharmacy_inventory","parameters":{"medication":"Ventolin 100mcg","location":"Algiers central"}}}
~~~

Each record needs a unique case_id that exists in the benchmark. For tool-call cases, include tool_call in the exact shape shown in the benchmark. The runner reports missing cases as failures. It rejects unknown and duplicate IDs. It writes reports/latest_regression_report.json and exits with code 1 when any check fails or 2 on invalid input. The example fixture should pass, which validates the runner—not any model.

## Run the web workbench

~~~bash
npm ci
npm run dev
~~~

Open http://localhost:3000. The UI is a static/heuristic prototype, and its built-in responses and values must not be interpreted as live API results.

## Next steps before treating this as a production evaluation tool

1. Build a full, versioned benchmark with clear source/provenance, inclusion criteria and enough cases to cover intended use.
2. Add provider adapters that store model identifier/version, prompts, parameters, raw output, timing and token usage.
3. Replace substring-only checks with validated metric implementations and human-reviewed reference labels; document metric limitations.
4. Add test cases that must fail, including regression tests for threshold enforcement, missing outputs, malformed tool calls and prompt-injection attempts.
5. Run separate, reproducible calibration, latency and cost studies where those are required.
6. Keep claims narrowly scoped to the cases, methods and data actually measured.

## Repository layout

- benchmarks/benchmark_suite_v1.json — Four hand-authored smoke cases.
- examples/illustrative_responses.jsonl — Clearly labelled test fixture, not measured model output.
- scripts/run_eval.py — Deterministic evaluator.
- tests/test_eval_gates.py — Unit tests for pass/fail behavior and input validation.
- reports/latest_regression_report.json — Last runner-generated report; overwritten when the runner is executed.
